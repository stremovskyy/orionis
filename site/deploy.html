Orionis/Deploy

A clear path to production.

Run Orionis with YAML by default, keep legacy JSON configurations working, and deploy to ECS with configuration and signing keys in their proper places.

1. Run with Docker

The published auth-server image is available from Docker Hub and GHCR for linux/amd64 and linux/arm64. Pin a release tag in deployed environments.

Shell · choose either registry 
docker pull stremovskyy/orionis:0.7.0
# Equivalent mirror:
docker pull ghcr.io/stremovskyy/orionis:0.7.0

From the repository root, create a YAML config on a fresh checkout. Keep an existing orionis.json if you are upgrading: the new image loads it when no YAML config is present.

Shell · prepare the config 
if ! test -f config/orionis.yaml && ! test -f config/orionis.yml && ! test -f config/orionis.json; then
  cp config/orionis.example.yaml config/orionis.yaml
fi

Mount the config read-only and keep generated demo keys in a separate named volume:

Shell · run the published image 
docker run --rm -d \
  --name orionis-auth \
  -p 8080:8080 \
  -v "$PWD/config:/app/config:ro" \
  -v orionis-var:/app/var \
  stremovskyy/orionis:0.7.0

Or use Compose.

After preparing the config, use this as an alternative to the command above; both bind port 8080.

Shell · release Compose 
ORIONIS_IMAGE_TAG=0.7.0 docker compose -f docker-compose.release.yml up -d

To run the full source-built demo stack, including billing and orders, use:

Shell · complete demo
docker compose up --build --wait -d orionis-auth billing-api
docker compose run --rm orders-client
Generated keys are for local development

The demo can create signing keys in /app/var. For production, provision stable private keys and inject them through private_key_pem_env. Replace the sample client credentials before sharing an environment.

2. Choose your configuration

YAML is the default for local files and the Docker image. JSON remains supported for existing configurations and explicit file paths. Orionis detects either format from its content, regardless of filename, extension, or AppConfig content type. Both use the same snake_case fields and runtime validation.

Shell · default YAML or explicit legacy JSON 
go run ./cmd/orionis-auth
# To select a legacy JSON file explicitly:
go run ./cmd/orionis-auth -config ./config/orionis.example.json

Without -config or ORIONIS_CONFIG, Orionis looks for orionis.yaml, then orionis.yml, then orionis.json in config/. In a source checkout with none of those, it loads the YAML example, or the JSON example if YAML is absent. An explicit -config path takes priority over ORIONIS_CONFIG.

These equivalent excerpts illustrate the shared field names. The full checked-in examples also define signing keys, clients, and operational limits.

YAML · configuration excerpt 
issuer: http://localhost:8080
access_token_ttl: "15m"
JSON · legacy equivalent 
{
  "issuer": "http://localhost:8080",
  "access_token_ttl": "15m"
}

YAML must contain exactly one document. Durations use strings such as "15m". A present but invalid YAML file fails startup instead of silently loading JSON.

See the complete YAML example and legacy JSON example.

3. Deploy on AWS ECS

On Fargate, start Orionis with -config aws. Configuration and private signing keys arrive through separate paths.

Set the identifiers for an already deployed AppConfig configuration:

Environment · required AppConfig identifiers 
AWS_REGION=eu-central-1
AWS_APPCONFIG_APPLICATION=<APPLICATION_ID>
AWS_APPCONFIG_ENVIRONMENT=<ENVIRONMENT_ID>
AWS_APPCONFIG_PROFILE=<CONFIGURATION_PROFILE_ID>

Reference the injected signing key by environment name in the config. This excerpt is part of a complete production configuration:

YAML · signing-key reference 
active_kid: signing-key-2026-10
keys:
  - kid: signing-key-2026-10
    private_key_pem_env: ORIONIS_SIGNING_KEY_PEM

Store client secret digests in secret_sha256_hex arrays. Keep plaintext caller credentials in the callers’ secret stores; keep private-key PEMs in Secrets Manager.

AWS role responsibilities
Role Required access
Task role AppConfig StartConfigurationSession and GetLatestConfiguration for the selected configuration.
Task execution role CloudWatch Logs and GetSecretValue for the signing-key secrets ECS injects.

Use the checked-in ECS templates and deployment guide with the YAML AppConfig example for AppConfig creation, scoped IAM policies, task-definition rendering, networking, and service setup.

4. Roll out changes

A new AppConfig version takes effect when new Orionis tasks start. Use this order for a configuration rollout:

For an existing ECS service, retain the current task-definition ARN and configuration version for rollback. After the AppConfig deployment completes, replace tasks using your configured cluster, service, and task definition:

Shell · rolling task replacement 
aws ecs update-service \
  --cluster "$ORIONIS_ECS_CLUSTER" \
  --service "$ORIONIS_ECS_SERVICE" \
  --task-definition "$ORIONIS_TASK_DEFINITION" \
  --deployment-configuration 'minimumHealthyPercent=100,maximumPercent=200,deploymentCircuitBreaker={enable=true,rollback=true}' \
  --force-new-deployment

Set ORIONIS_TASK_DEFINITION to the task-definition ARN or revision you intend to deploy. Keep issuer and signing-key references stable when changing configuration delivery. Rollback of an AppConfig change requires restoring the previous configuration and replacing tasks again; an old task definition alone still loads the currently deployed AppConfig version.

5. Verify the result

Check the local server, or replace the base URL with your deployed HTTPS endpoint:

Shell · health and public metadata 
curl -fsS http://localhost:8080/healthz
curl -fsS http://localhost:8080/readyz
curl -fsS http://localhost:8080/.well-known/openid-configuration
curl -fsS http://localhost:8080/.well-known/jwks.json
JSON · health / readiness response 
{"service":"orionis-auth","status":"ok"}

If base_path is configured, include it in every URL and health check. Then follow the token and protected-request walkthrough. For the complete local demo, expect 201 from billing; also confirm that a missing token returns 401 and an insufficient scope returns 403.

Readiness is the first check

A healthy task proves initialization succeeded. Issuing a token and using it at a protected API proves the integration. During replacement, also verify that previously issued tokens still validate.
